# C 一跳/两跳扩展修复与验收

## 根因与证据边界

本轮访问本机 8002 返回 ConnectionRefused，没有监听服务，因此没有把隔离测试冒充当前 Docker 在线验收。使用原始 effective.json 完整150篇、相同 revision，在独立 Neo4j Harness 5.26.0 的17697端口复现旧查询并验证新查询；测试结束后引擎已停止。未修改 Docker、发布指针、B/D 或执行 Git 命令。

主要问题：

1. 后端原本确实用 `*1..hops` 做无向1—2跳遍历，不是忽略 hops；但 `RETURN path LIMIT` 没有按长度排序，混合深度路径的执行顺序不保证一跳先保留。以实测论文为例，旧两跳结果甚至丢掉了一跳中的11个节点，不能当作稳定的逐步展开。
2. 前端确实从下拉框读取 hops，并在点击加载时重新请求，没有缓存命中造成“一直读一跳”。但原先没有一跳基线和新增 ID 集合，只按度数截取60节点。默认选中中心时，非直接邻居及边会被淡化，恰好淡化了二跳部分。
3. 服务端是路径数量上限，前端是节点上限，两者不同。大邻域中新增内容可能被截断或隐藏，不能用屏幕节点数字相同推断后端没有扩展。
4. `/research` 还沿用当前标题/主题/方法等筛选，查询要求路径上的论文满足这些条件。例如只检索特定论文标题，会排除同会议的其他论文，只剩较少的二跳机构；这是原有筛选语义，未为了演示取消它。`/research/analytics` 的关联图默认按指定批次与起点探索。比较两个页面必须采用同样筛选范围。

## 最小修复

- 保留无向遍历设计，输出仍使用 startNode/endNode 的真实方向。按路径长度、终点类型和稳定节点/关系 ID 排序后再 LIMIT，优先保留一跳；二跳同长度优先机构等节点以增加异构关系可读性。没有添加任何科学关系。
- 新增响应字段 traversal_policy=shortest_paths_first；健康检查标识升级为 c-effective-graph-v3，便于确认实际运行代码。
- 两个页面继续复用唯一的 graph-view.js。加载二跳时，分别请求同一批次、同一起点、同一预算的一跳和两跳，按节点/关系 ID 去重比较，保留已取得的一跳基线。
- 一跳节点优先进入60节点画布，二跳新增节点使用紫色虚线边框，新增边使用紫色虚线；默认中心选中时不再淡化整个二跳。类型颜色仍保持原含义。布局仍为力导向，标签数量仍受限。
- 显示已加载跳数、响应总量、画布量、相对一跳的新增节点/关系量与画布中实际显示的新增节点量。下拉框变更本身不请求，必须点击“加载 / 展开”。
- 未截断且无新增时明确提示“没有发现新的两跳关联”；截断且无新增时改为提示“当前截断范围未见新增”，不宣称源数据没有更多关系。
- 区分服务端路径截断与画布60节点截断。若一跳已占满画布，两跳新增可能未显示，应筛选类型或选择节点后点击“从此节点重新探索”，以新的中心重新加载一跳，再手动扩展。
- 每次加载重新请求；重复点击不累加节点，晚返回的旧请求不能覆盖最新图。销毁组件会使待返回请求失效。
