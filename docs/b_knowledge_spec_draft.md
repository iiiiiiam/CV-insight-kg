# B 实体、关系与证据规范提案

版本：`b-knowledge/0.1-draft`。状态：B 本地原型草案；不是团队正式接口。

本文基于当前 Team 输入代码和固定样本整理。用户同意先做“提及”候选并继续开发后，
已实现内存候选模型、初始词表、抽取和校验，详见 `b_candidates.md`。
第 5 节的审核操作已实现，见 `b_review.md`；本地持久化见 `b_review_storage.md`，正式业务导出仍待实现。

## 1. 八类实体及首版区分方式

| 类型 | 建议英文值 | 含义及边界 |
| --- | --- | --- |
| 论文 | `paper` | 一篇论文，沿用输入的 OpenAlex ID |
| 作者 | `author` | 元数据中具名的作者，不凭同名合并 |
| 机构 | `institution` | 该论文 authorship 中关联的机构，不推断当前任职 |
| 主题 | `topic` | 较宽研究方向，如 computer vision；不自动复制所有任务为主题 |
| 方法 | `method` | 模型、算法或技术，如 RT-DETR、knowledge distillation |
| 任务 | `task` | 要解决的问题，如 object detection |
| 数据集 | `dataset` | 研究数据资源，如 COCO；区别于输入的样本集编号 dataset_id |
| 会议/期刊 | `venue` | 发表载体；当前从输入的 venue 读取 |

建议先使用小型人工词表，分别声明类型、规范名称和允许的别名。
只按已列出的别名匹配，不靠去标点或包含关系自动合并不同名称。
同一规范项可在多篇论文复用；未知词、缩写冲突保留为未覆盖问题，不猜测。
首版主题词表可以很小；八类模型齐全不代表每篇论文都必须产出八类候选。

## 2. 七类关系与首版方向

建议首版使用较保守的文本“提及”关系。词表命中本身不能证明论文使用、提出或评测了某项内容。

| 起点 | 关系英文值 | 终点 | 候选依据 |
| --- | --- | --- | --- |
| 论文 | `has_author` | 作者 | 输入 authorships 中的作者记录 |
| 作者 | `affiliated_with` | 机构 | 同一 authorship 中的作者与机构关联，仅限该论文上下文 |
| 论文 | `published_in` | 会议/期刊 | 输入 venue，来源为已校验清单 |
| 论文 | `mentions_topic` | 主题 | 标题或摘要中的词表命中 |
| 论文 | `mentions_method` | 方法 | 标题或摘要中的词表命中 |
| 论文 | `mentions_task` | 任务 | 标题或摘要中的词表命中 |
| 论文 | `mentions_dataset` | 数据集 | 标题或摘要中的词表命中 |

例：首篇论文摘要同时讨论 YOLO 和 RT-DETR。两者都可成为方法提及候选，
不能仅凭出现名称就将 YOLO 标成该论文提出的方法。
如以后需要 uses_method、proposes_method 或 evaluated_on，应另行定义语义和判定规则。

## 3. 标识与模型分工

- `Entity`：类型、规范名称、实体键、可选的来源 ID。
- `Evidence`：该篇输入内的原文或元数据定位，见下一节。
- `EntityCandidate`：某论文中的实体候选，引用实体及证据。
- `RelationCandidate`：起点实体键、关系类型、终点实体键和证据；始终保留该论文 ID。
- 同一论文同一关系两端的重复命中合并成一个候选，保留不同证据。

建议实体键规则：论文/作者/机构有 OpenAlex ID 时以“类型 + 来源 ID”区分；
词表实体用人工指定的稳定词条键，显示名称和别名修改不改变键。
venue 当前输入只有名称，首版使用 `venue:local:` 加原始名称，不冒充 OpenAlex 来源 ID，
暂不自动合并会议别名。
作者或机构缺少来源 ID 时用“论文 ID + authorship 位置 + 机构位置”等定位生成本地键，
并标记未解析；不凭姓名跨论文合并。

建议候选 ID 由版本、论文 ID、候选种类及实体键/关系两端确定性生成。
同一输入和词表重跑可得到相同候选 ID；词表版本、规则版本和输入指纹另行记录。
这些均为 B 本地键，不替代 A 的 openalex_id，也不提前规定 C 的数据库主键。

## 4. 证据位置与输入变化

每条证据记录论文 openalex_id、dataset_id、source_url 和实际输入指纹。
输入指纹按明确序列化规则计算，覆盖 PaperInput 全部字段；不能只依赖论文 ID。

文本证据记录：

- `field`：`title` 或 `abstract`。
- `start`、`end`：Python 字符串的字符索引，左闭右开，不是 UTF-8 字节数。
- `quote`：输入字段的精确切片，校验 `text[start:end] == quote`。
- 摘要位置只针对 B 还原的摘要，不是 PDF 页码、原文段落或 PDF 字符位置。

真实样本：`https://openalex.org/W4402754006` 的标题为
`DETRs Beat YOLOs on Real-time Object Detection`。
本轮实际读取所得 `title[30:46] == "Object Detection"`。
它只能支持任务提及候选，不能代替人工审核。

元数据证据记录结构化路径和该位置值，例如：
`["authorships", 0, "author", "id"]`、
`["authorships", 0, "institutions", 0, "id"]`、`["venue"]`。
路径相对于 PaperInput；venue 的值来自清单，不声称原始 JSONL 中存在同名字段。
作者—机构关系需同时引用同一 authorship 的作者及机构定位。

先校验位置和值，再允许生成候选。输入变化时旧证据必须重新校验，不能静默套用。
缺失摘要不产生摘要证据；缺少必要作者或机构信息不猜测，记录诊断信息。
原始来源本身可能有错误，位置校验只能证明“输入里确有此内容”。

## 5. 当前内存审核边界

建议候选统一初始为 `pending`；人工决定为 `confirmed` 或 `rejected`。
元数据转换同样只生成待审核候选。
人工纠正应保留原候选和修改前后记录，修改后重新验证类型、关系两端及证据。
候选与已确认知识分开输出；只有人工确认且校验通过的内容才能进入已确认集合。
确认关系时须确保两个端点均已确认；首版要求逐个明确确认，不隐式代替用户确认端点。

当前已实现待审核候选及校验、内存确认/驳回/纠正/撤回及操作事件。
首版纠正限显示名称和证据，不改身份、类型、关系方向或端点。
已确认实体撤回时，其已确认关系同步退回待审并记录事件。
文件保存与恢复已实现，版本为 `b-review-file/0.1-draft`，绑定输入和原始抽取结果并重放历史校验。
正式业务导出及更复杂的身份/类型纠正后续单独完成。

## 6. 本阶段实现和验收范围

1. 扩展集中模型，保留现有 PaperInput 和输入读取行为。
2. 新增带版本的小词表及规则抽取器：元数据关联、标题/摘要词条命中。
3. 对全部 20 篇真实样本运行，检查关系端点、证据切片及元数据路径。
4. 使用 unittest 验证误匹配边界、别名、重复命中、缺失字段和非法证据；构造数据仅用于程序测试。
5. 报告实际候选数量和未覆盖问题；不将程序测试通过或候选数量表述为准确率达标。

暂不包含 UI、A 的 API 扩展、数据库改动、在线采集和 C/D 的正式契约。
首版只做词表提及，可能漏掉词表外名称，也可能抽到背景讨论或否定语句中的提及。
正式评估集划分、人工校准及至少 5 篇人工确认演示仍需后续完成。
