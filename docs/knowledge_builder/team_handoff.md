## 2. 现在能做什么

- 知识与证据页：查看原文依据、单篇关联图，按标题和子方向组合筛选。支持 17 个方向及“其他”。
- 管理员页：导入论文批次、查看新增/重复/更新/失败数量、撤回批次；原来的用户反馈处理保留，两个页签共用导出按钮。
- 批次处理：同 ID 论文只留一份；采用后接收的有效内容。撤回第二批后，第一批仍提供的论文保留，只由第二批提供的论文退出。
- 来源补充：复用已有信息，后台补充缺少的来源。获取不到时保留规则识别结果，可重试。新旧论文共用同一识别流程，不保证每篇都能找到外部信息。
- 有效结果：导出当前完整结果和内容版本，包含公共修改，不包含浏览器个人调整。自动生成不等于人工确认。

批次、来源增强及筛选均有相关自动测试，前端构建通过。原 150 篇来源复用和模拟批次的合并、撤回已离线验证；真实来源网站可用性、A 的正式两批和 C/Neo4j 发布未在本轮完成验收。

## 3. 原来的 150 篇与后续论文，是什么关系

**150 篇是原来的演示输入，不是已经登记好的正式基线批次。** 目前有两种输入方式：

| 当前方式 | 显示的论文 |
| --- | --- |
| 还没有成功导入批次 | 原配置中的样本，通常为 150 篇 |
| 已经成功导入批次 | 当前账本中所有生效批次合并后的论文 |

首次成功导入会**切换输入**，不会自动在 150 篇后追加。原样本文件没有删除，只是当前不用它们。因此练习中的 20→30→20 是两批合并、撤回的结果，不是原 150 篇丢失。撤回全部批次会得到 0 篇，不会恢复样本。

**下一周请组长结合整体集成选择数据方案，不在本轮擅自决定：**

| 可选方案 | 还需要做什么 |
| --- | --- |
| 保留 150 篇作为基线，后续追加 A 的论文 | 先由程序把 150 篇一次性登记成基线批次，再接新批次；重复 ID 自动去重。目前未提供一键迁移。 |
| 正式论文统一按 A 的批次管理 | 不强制保留演示 150 篇，以 A 的交接批次决定范围；目前已有导入、合并和撤回能力。 |

两种方案都不需要人工重抄论文。原 150 篇若也包含在 A 的正式批次中，可按同 ID 自然接入。**不要直接把“150＋新增数”当成当前总数，也不要认为拉代码就自动取得本机样本缓存、批次账本或验收数据。** 本地 data 文件默认不随 Git 推送。

## 4. 其他成员怎么查看

1. push 后获取 `knowledge-topics` 的最新代码，合并由组长安排。
2. 沿用自己的项目环境和管理员账号。重启后端 `python -m server.run` 加载新接口；前端在 frontend 目录执行 `npm.cmd run dev`。只体验 B 不需要 Neo4j。
3. 打开 `/research/knowledge`，查看子方向筛选、依据和单篇关联图。
4. 管理员打开 `/admin/knowledge-feedback`，在“用户反馈 / 论文批次”切换。**只看页面无需导入；导入会改变本机当前论文范围。**
5. 真实两批联调留待组长安排，届时按最新集成版本确定操作步骤；当前不用额外执行。
