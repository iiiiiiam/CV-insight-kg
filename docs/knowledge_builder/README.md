### 当前已实现：独立阅读与反馈闭环

- 公开入口 `/research/knowledge`：正常展示现有论文知识，点对象/关系查看原文高亮或来源字段，不显示待审标签；A 原始论文详情也复用新证据组件。
- 个人隐藏、改名及补充主题/方法/任务/数据集，只写当前浏览器的 localStorage；B 页面内列表与单篇关联图同步更新，可撤销、恢复默认。个人操作不调用反馈接口，不弹窗要求反馈。
- 图与详情按组件实际宽度布局：宽区域并排，窄区域选节点后自动定位详情；改名在详情内直接编辑。主要操作使用大按钮，工具条保留撤销上一步、调整记录与恢复全部默认。B 单篇图由浏览器直接绘制现有对象/关系，不需要 Neo4j；跨论文、多跳查询仍属于 C 的正式图谱链路。
- 支持具体条目纠错与论文中遗漏名称反馈。提交问题不会直接隐藏信息；重复未处理反馈复用编号。
- 管理入口 `/admin/knowledge-feedback`：复用现有登录/CSRF，按反馈队列处理保留、显示名修正、不采纳，以及核实后的补词；状态计数可点选筛选。
- 用户提交后可在详情中的“我的反馈”撤回当前浏览器提交的待处理申请；撤回后不出现在后台审核列表、全部反馈或统计中，用户自己的记录显示已撤回。底层保留记录以防重复处理。已处理申请和无浏览器凭证的历史记录不能直接撤回。撤回反馈不会恢复个人视图，也不会反向修改公共知识。撤回使用 POST 请求体中的随机凭证，后台仅存摘要，与管理员会话分开。
- 保留原有三级菜单导航，页面入口的突出方式交由前端同学统一设计，不另加顶部快捷按钮。用户选择问题类型即可反馈，补充说明选填；管理员直接查看条目与原文依据、保存前查看公共影响，处理说明选填（缺省记录实际动作）。补词仍保留类别、别名、公开来源检查，不凭一条反馈直接自动改全局规则。
- 管理员可对已处理或已说明保留的反馈执行“撤回处理，重新待处理”：只移除该次处理对应的公共修正/补词，反馈恢复待处理，原处理移入历史。用户可在刷新本人反馈状态后再撤回上报。若其他公共处理依赖该词条，需要先撤回依赖处理；不会用整份旧存档覆盖其他结果。已由用户撤回的反馈不能被管理员重新打开。
- 通过遗漏申请补充规范词或已有词的新别名，要求类别、公开依据与处理理由。新结果仍由程序重新提取，不改写源词表或手填论文结果。
- 数据写在当前审核目录下的 `_feedback/state.json`，默认是 `data/knowledge_builder/reviews/_feedback/state.json`；与第一周审核 JSON 分开，不给旧候选制造确认事件。

这条独立链路只需 D 服务和 Vue 前端即可查看，不依赖 A HTTP 服务或 Neo4j 在线；输入仍来自 A 的固定 20 篇文件。**反馈补词与纠正目前只作用于新阅读视图和本轮反馈存档，旧 CLI/confirmed 导出、C 图谱发布尚未消费它们。** 不把此阶段写成全组自动知识协议已接通。

### 已确认的产品规则

根据用户与 C/D 已沟通的决定：

- 自动整理结果正常展示，不要求逐条人工确认后才能查看。
- 普通阅读页面不显示“未经审核”“待确认”或同义状态标签；只提供“如有错误，可反馈”的入口。
- 管理员人工审核只处理用户提出的反馈，不把所有自动条目放入全量待审任务。
- 来源、原文依据、提取版本、实际处理历史在内部保留，查看依据时可追溯；不伪造人工确认。
- 收到反馈只是收到疑问，不等于原结果有错，也不自动隐藏该内容。管理员处理后再依实际结论纠正或不采纳。

**产品方向已确认，不再反复询问是否接受自动结果。** 但当前第一版代码仍有 confirmed-only 导出和图谱限制，需要第二轮实现和联调，不能把本节当作新行为已经上线。底层数据真实性与公开页面的提示方式分别处理：不显示未审核标签，不代表要伪造 reviewer 或 confirm 事件。

方法、任务、数据集不是有作者和摘要就自动齐全；优先沿用已有自动程序和真实来源字段。**不由编码助手手工阅读样本、填写一批关键词作为产品提取结果**，也不把这些答案写死成只适用于演示论文的规则。

### 先独立完成，再联动

1. **独立阶段：** 复用现有 20 篇及自动提取结果，把 B 的证据阅读、反馈提交、管理员处理和状态统计串成闭环。优先使用 `src/knowledge_builder/` 和独立知识/反馈组件；不另建一个仅用于演示的 Streamlit 前端。
2. **输入阶段：** 与 A 确认新批次文件、来源字段、稳定 ID 和版本；B 做适配，不接管 A 的采集与数据管理可视化。A 尚未交接的内容不假装已经覆盖。
3. **联调阶段：** 与 C 确认自动结果协议，与 D 接公共身份、导航和工作台上下文；核对新结果进入查询、证据查看、处理后更新的实际链路。
4. **验收阶段：** 真实处理案例、存档恢复、导出兼容、必要回归和实际页面检查。汇报分清已完成、待接入和实际数据范围，不按原参考计划虚报完成。

第一轮已存在不少基础能力。本轮不是把确认按钮或证据表格重新做一遍，而是改变展示与审核的使用流程，让信息阅读和反馈处理形成直观联动。

### 提取策略：本轮保留可重复运行的基础

- 标题、作者、机构、年份、摘要、来源等优先直接复用 A 已提供的结构字段。
- 方法、任务、数据集等先用现有自动提取和词表匹配，保守表达“提及”，不扩展成提出/使用/实验优劣判断。
- 来源若已提供主题或关键词，先检查真实样本和字段含义，再复用；关键词不自动等于方法或数据集。当前原 20 篇的抓取字段没有 topics/keywords，不能假设它们已经存在。
- 词表可以在开发阶段适度扩充，由开发者结合类别、公开出处、歧义和实际用途判断；补齐当前领域常用名称，不以原有 53 条为上限，也不为追求数量无限扩表。
- 本轮不接入大模型、全文 PDF 理解、复杂消歧、大规模词表管理平台或新的研究用户账号体系。

### 词表准入与遗漏反馈：适中、可维护、可复用

本轮不是极少数名称的演示清单，也不是穷尽全部论文术语。按“优先用 A 的结构字段，再以词表补充”建设当前研究范围内较充分、规模受控的识别能力：

| 内容 | 准入方式与边界 |
| --- | --- |
| 公开数据集，例如 LVIS | 名称、类别和公开出处清楚，有识别价值，可收录规范名及必要别名；不要求先走复杂审批 |
| 会议/期刊，例如 CVPR（会议） | 优先用 A 已提供的发表载体字段；词表/别名可辅助统一名称，不重复造冲突对象。若要匹配摘要中的会议名，应先明确该类识别规则，不把它硬塞进方法或数据集 |
| 方法、任务和研究主题 | 正式名称及类别明确、与当前研究方向有关时可收录；不局限于某一篇演示论文 |
| 模糊缩写、普通词和一次性短语 | 谨慎收录或采用更完整写法，不仅凭一次出现就扩词，避免引入大量误匹配 |

开发者可以判断哪些词值得加入，并记录来源与原因；**判断词条准入不等于用编码助手手工替每篇论文填写识别结果**。加入词表后，仍由同一套程序对当前与新增论文匹配、生成证据，保证不依赖助手逐篇读过样本。

反馈分两条：①已经显示但有误，针对对象/关系处理；②应识别却未显示，针对论文提交遗漏名称和原文位置/描述，不要求用户先选一个不存在的候选。管理员核实类别与歧义后，可新增规范词或别名，再按更新后的版本重新提取并检查效果；不直接信任反馈内容，不把原文没有的名称加成论文结果。

“后台加入词表”纳入本轮轻量维护范围：支持必要的新增/别名修订、重复与类别检查、依据和版本记录，并能看到重新提取的结果；不扩展成完整词表运营平台、自动学习或任意修改知识类别的系统。

词表改变可能影响多个论文的识别结果与输入提取指纹。重新提取与结果生效需显式处理版本：保留旧存档和真实决定，不把旧核对盲目套到新结果，不覆盖历史；涉及 C 已发布数据时按约定更新快照。处理反馈不能只显示“已加词”，却仍让用户看不到对应的新结果。

新增词优先来自通用覆盖缺口和用户实际反馈，定期检查重复、别名歧义和误匹配，不设为了汇报必须凑齐的词数。遇到现有规则不能可靠识别的情况，说明处理限制；本轮不承诺精确理解上下文，也不将“提及”升级为“使用/提出”。

### 必要的协作边界

| 对方 | B 提供/需要确认什么 | 不由 B 独自承担什么 |
| --- | --- | --- |
| A | 新批次交接格式、原始文本和作者机构结构、来源/缺失字段、稳定 ID、输入版本 | 数据源采集、A 数据库任务、数据管理概览和来源分布页面 |
| C | 自动结果与真实处理记录的协议、证据、对象端点、版本；不再强制每条都有人工审核人 | Neo4j 内部实现、作者画像与研究统计 |
| D | B 自己完成的证据/反馈模块，以及公共导航、身份与研究上下文的接入约定 | 全部研究图表、公共样式和全局路由改造 |

只在确有接入需要时协商修改共用文件，不顺手重构 `server/`、整个 `frontend/` 或其他成员目录。源数据、状态与批次兼容保持清楚；新协议不通过批量改旧 pending 为 confirmed 来实现。普通用户不看审核标签，内部仍保留真实来源与变更。

反馈处理与 C 已发布快照的同步方式需约定：当前版本按批次发布，B 本地处理后不自动改写旧快照。本轮先复用发布机制，新版本生效前由维护端说明同步情况；不默认加自动增量发布系统。公开页面继续正常展示，不额外附加“未经审核”标签。

### 验收与这一周的意义

最小可演示场景：打开一篇论文→点方法或数据集看到原文→隐藏、改名或补充个人条目，列表与单篇图立即同步且不生成反馈→刷新保留或撤销。确需公共纠错时，再主动提交反馈→管理员处理；若需补词则核实后加入并重提取→反馈状态、统计与结果更新→必要时把新结果交给 C/D 生效。

如果实际核对后原结果无误，也可以说明理由关闭反馈；不为了制造案例故意改坏真实数据。自动化测试里的反馈是测试用例，不冒充真实用户报告或人工标注。

本周价值是把 A 提供的记录整理为**可关联、可查证、能纠错补漏并持续改善覆盖**的信息，再交给 C/D 用于研究展示。自动识别先用可维护的来源字段与词表，人工投入集中在反馈和合理词条维护，而不是逐条审核所有结果。保留必要回归验证，不将删除测试或 workflow 作为本轮交付。图表、存档与案例都来自真实操作，不写死演示数字。

### 个人调整与主动反馈（2026-11-06 修订）

本阶段按“自动展示→个人按需调整→必要时主动反馈→后台维护公共规则”设计，不再把用户的每一次修改当成反馈。个人隐藏、改名和补充仅保存在当前浏览器；列表和 B 知识页的单篇关联图使用同一份调整结果，刷新后可恢复，也可恢复默认。保存个人调整不调用反馈接口，不要求填写理由，不主动弹窗。

只有用户从“更多操作”主动进入反馈表单并点击“提交反馈”，后台才收到问题。个人补充不伪装成自动识别或原文证据；个人名称修改保留原有证据引用。公共结果版本变化后，旧版本个人调整暂停应用并在页面内说明，避免错误覆盖新的公共结果。个人设置不跨浏览器、设备同步。

实现先限于 B 的知识与证据模块及其单篇图，不直接修改 C 的 Neo4j 数据或 D 的正式研究图谱。C/D 目前的人工确认批次限制仍需协同修改；不能把 B 页面图谱可用描述为全组图谱已完成自动结果接入。

## 从仓库根目录运行

复用已有 insight 环境：

```powershell
conda activate insight
python -m scripts.knowledge_builder.preview
python -m scripts.knowledge_builder.prepare_validation
python -m scripts.knowledge_builder.export
```

第一条看候选；第二条生成质量报告、五篇验证材料和空白答案；第三条导出分开的已确认、待审和驳回文件。
需要时再使用审核入口，不要求现在逐条审核：

```powershell
python -m scripts.knowledge_builder.review --paper-index 1 --reviewer "你的姓名"
```

全部命令均支持 --help。查看旧词表结果加：

```powershell
python -m scripts.knowledge_builder.preview --vocabulary examples/knowledge_builder/vocabulary_v0.1.json
```

团队全套测试仍是：

```powershell
python -m unittest discover -s tests -v
```

测试会导入 A 的数据库模块；建议在单独终端先设置 `$env:DATABASE_URL = 'sqlite://'`，结束后关闭该终端或恢复原值。

## 重构兼容说明

旧 scripts.*_b_* 命令名已经替换为上面的功能命令；不保留同名空壳代码文件，避免两套入口长期并存。
Python 核心调用方式 `from src.knowledge_builder...` 不变。
既有存档、候选编号、业务文件版本及证据保持兼容；已经写入数据的格式标识不随文件重命名，以免旧 ID 和存档失效。
本机已有的运行目录已按功能整理到 data/knowledge_builder 下，文件内容不改。
其他机器若仍有旧审核目录，默认路径会识别它；新旧目录同时有记录时要求显式选择 --reviews-dir 或 --archive，避免混读。
旧阶段产物中若有旧命令文字，可按本页的新入口重新生成验证材料，不改写已生成文件的校验值。
