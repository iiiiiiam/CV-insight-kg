# B 批次接入与撤回

已实现 B 内的批次账本、合并、撤回、离线导出，以及管理员网页和接口。A 的采集和 C 的图谱代码不改，不自动扫描或读取 A 的数据库。首次成功导入前，网页仍用原有数据；导入成功后，阅读、反馈和 effective 导出统一使用批次集合。

## 管理员网页操作

打开现有 `/admin/knowledge-feedback` 页面，选择“论文批次”。不用新增导航，也不需要启动 Neo4j。

1. 选择 A 导出的 `a-paperinput/1` JSON，核对显示的批次号和论文数。
2. 阅读提示并勾选确认，点击“导入并更新 B”。首次导入会切换输入范围，原有 150 篇不会自动合并，旧样本文件和反馈存档保留。
3. 查看新增、更新、重复或逐行错误；失败时整批不生效，修正文件后重试。
4. 查看“来源补充”进度，等待后台补充完成后刷新知识与证据页；两个页签上方共用“导出当前有效知识”按钮。
5. 在批次列表点击“撤回批次”，阅读影响说明后确认。全部撤回后，当前输入为空，不回退到旧样本。

默认账本为 `data/knowledge_builder/batches/ledger.json`。服务端可通过 `B_BATCH_REGISTRY` 指定其他路径；启用批次模式后使用账本同目录的 `feedback/state.json`，不混入旧体验记录。命令行与网页只有在使用同一账本路径时才共享数据。

导入和撤回会影响当前有效导出，因此现有 D 自动同步逻辑也可能读取新结果并尝试发布；本次没有修改该逻辑。C 不可用不妨碍 B 保存批次。空结果能否由 C 发布尚需验证，不表示整组联调已完成。

批次论文已复用原有来源增强流程：优先使用 `B_SOURCE_CORPUS` 中内容相同的记录，再复用公共来源请求缓存；缺少的 OpenAlex/外部目录信息在导入后后台获取。来源记录必须通过校验和与论文身份匹配，不把来源标签伪装成原文依据。网页读取、反馈和导出不联网。

补充快照放在账本同目录 `sources/`，按实际论文内容区分，忽略仅 dataset_id 的变化。论文内容更新不套用旧记录；撤回更新批次后可重新使用旧内容对应的记录。新增记录会影响有效知识版本，处理进度、失败说明不冒充知识内容。来源不可用时保留词表及原文规则识别，已取得的来源不因重试失败而删除。

“来源补充”显示已处理、有来源及部分缺失数量；导入后自动开始，旧账本或中断后可点“补充未取得的来源”。完成后刷新知识页、重新下载导出。后台补充过程可能产生多个内容版本，前一次下载不会自行更新。缺少来源不代表论文已被人工确认或识别已完整。

`B_SOURCE_CACHE` 可指定请求缓存目录，默认复用 `data/knowledge_builder/source_cache`；`B_SOURCE_OFFLINE=true` 时只使用本地来源与缓存，缺失记录可随后联网重试。A→B 自动传递仍未接通，C 实际发布本机仍未验证。

## 管理接口

以下均使用现有管理员会话；POST 还必须携带 `X-CSRF-Token`。由网页或程序调用，不是终端命令。

- `GET /api/admin/knowledge/batches`：读取列表、最近失败、当前论文数和账本 `revision`。
- `POST /api/admin/knowledge/batches`：JSON 请求体 `{revision, document, acknowledge_switch: true}`，其中 document 是 A 的完整批次文件内容。
- `POST /api/admin/knowledge/batches/{batch_code}/withdraw`：请求体 `{revision}`。
- `POST /api/admin/knowledge/batches/enrich`：无需请求体，在后台补充当前论文缺失的来源；需要管理员登录及 CSRF。已有任务运行时复用该任务，不重复排队。

写入携带 GET 返回的整数 revision；期间有其他写入则返回 409，刷新后再操作。验证失败回执的 `status` 为 `failed`（HTTP 200），表示已记录失败尝试，不代表导入成功。认证、冲突、存档异常分别返回 401/403、409、503。前端文件选择限制为 10 MB。

## 输入和处理原则

- 接收 A 现有 `a-paperinput/1` 交接 JSON，保留 batch_id、batch_code、dataset_id、items、excluded 和数量信息。批次以 batch_code 为标识，batch_id 也必须与已接收记录一致。
- 每篇按规范 OpenAlex ID 合并。标题和摘要保持原样；不靠标题相似度擅自合并不同 ID。
- 同批次相同完整内容重跑幂等；已成功批次同名但内容不同报冲突，要求使用新批次号，不覆盖历史。
- 同一批中相同 ID/相同内容的重复条目只存一篇；同 ID 内容冲突则拒绝整批，不让排列顺序决定结果。
- 跨批次相同 ID 内容相同只记一个当前论文，但登记多个提供批次。比较内容时忽略 A 的 dataset_id 差异，避免仅批次号不同就误判论文更新。
- 同 ID 内容更新由“B 最近成功接收、且仍有效的批次”优先提供；不拿数字更大的 A batch_id 或论文年份猜更新时间。后收到的旧内容也可能成为当前版本，这是明确的接收顺序策略，未来有上游更新时间契约再调整。

## 数据集标识与原始来源

B 当前输入投影的 dataset_id 使用稳定的 `b-paper:<OpenAlex短ID>`，原始 A 的 dataset_id 保留在批次原文中，不覆盖 A 文件。这样两个批次提供完全相同论文时，不会只因批次来源切换就改变抽取证据指纹。标题、摘要、作者等实际输入变化仍会改变指纹，旧反馈不得套用。

快照保留每篇全部有效提供批次、当前选择的批次，以及输入内容指纹。批次原文和操作日志保留在本地账本，可追溯来源；不包含浏览器个人调整。

## 整批撤回，不等于反馈撤回

撤回批次会取消其提供资格，历史原文仍在。论文仍有其他有效批次提供时保留；只有被撤回批次提供的论文退出当前集合。更新版本来自被撤回批次时，恢复到剩余有效批次的最新版本。

重复撤回幂等。对已撤回批次重复导入原文不会暗中恢复它；若确需再次接收，使用新的批次号，避免误操作重启旧来源。未知批次不创建空记录。撤回全部批次允许生成明确的空当前集合；不替换成旧 20/150 篇。C 是否允许发布空图需另外确认，B 不代替 C 自动发布。

## 失败和重试：第一阶段采用整批原子接收

不是悄悄跳过坏行：任意输入条目无效时，整批不生效，返回逐条错误，保存失败尝试；旧快照保持可用。修正后可用同批次号重试，直到首次成功；成功后批次内容即冻结。原子保存失败不覆盖旧账本。

A 已列为 excluded 的记录保留在处理回执中，单独计数，不伪装成 B 已接收论文，也不把它们再当 B 异常处理。计数检查要求 exported_papers 与 items 数量一致、excluded_papers 与 excluded 一致，total_papers 为二者之和。

处理回执区分 accepted（本批唯一有效论文）、new、updated、duplicates、failed（B 无效条目）、not_applied（因整批失败未生效的条目）、upstream_excluded。重复可包括批内重复与跨批相同论文；它不是 accepted 的互斥分区，文档和界面不可简单相加。撤回回执区分 removed、retained、restored，并返回新快照版本。

## 版本和存储

账本使用校验封装、同目录临时文件和原子替换；用排他锁避免并发写入覆盖。锁冲突明确报错，不自动抢占。损坏账本报错，不当作空账本继续写。

当前快照根据排序后的有效论文和批次来源计算内容版本。失败尝试不改变该快照版本；重复成功导入不修改账本。成员来源变化可能改变来源快照版本，但论文内容不变时，既有 effective 导出的知识内容版本可以不变，两者用途不同。

## 与现有阅读和 C 的边界

离线命令和管理员接口均复用同一批次核心、来源快照、KnowledgeFeedback/effective_export，生成 C 已支持格式的完整有效知识。反馈使用独立路径，默认不混入旧 150 篇的体验记录。新增论文缺少来源补充时使用现有本地规则，不在导出时联网。

不绕过原固定语料的基线校验；批次输入是独立入口。网页切换、管理 API 和来源补充已接入；A 的自动更新/撤回通知和 C 的正式发布验收仍需后续处理。

## 必须验证的场景

1. 第一批甲乙，第二批乙丙：当前甲乙丙，乙只一篇；撤回第二批后保留甲乙。
2. 第二批更新乙：使用更新；撤回第二批后恢复第一批原文。
3. 同 ID 仅 dataset_id 不同：重复，不算内容更新，知识输入指纹稳定。
4. 同批重跑、重复撤回：幂等；成功批次同名不同内容：拒绝覆盖。
5. 坏行、坏统计、损坏账本、锁冲突、写入失败：旧有效数据保留；失败可追溯并可重试。
6. 读取当前集合并生成 effective，经过 C 现有离线校验；不实际启动或写入 Neo4j。

以上规则先于本阶段实现确定；若后续调整，先同步本文件，再改对应测试。

## 已实现的离线命令

在仓库根目录激活 `insight-prototype`。以下示例中的 A 交接文件路径和批次号需替换为实际文件，不是让使用者手工输入论文内容：

```powershell
python -m scripts.knowledge_builder.manage_batches ingest path/to/a-handoff.json
python -m scripts.knowledge_builder.manage_batches status
python -m scripts.knowledge_builder.manage_batches enrich
python -m scripts.knowledge_builder.manage_batches snapshot
python -m scripts.knowledge_builder.manage_batches withdraw BATCH-000002
python -m scripts.knowledge_builder.manage_batches export
```

默认账本：`data/knowledge_builder/batches/ledger.json`；默认导出：同目录 `effective.json`；默认反馈：同目录 `feedback/state.json`，不与旧 150 篇的存档混用。命令不读取 server/.env，不启用服务器或同步发布。

`enrich` 命令可获取外部来源，其他命令不会自动联网补充。全局 `--source-corpus path/to/corpus.json` 可复用旧语料；`--offline` 禁用来源联网。这些参数放在子命令之前。CLI 与网页使用同一账本时自动共享其 `sources/` 快照；CLI 不自动读取服务端配置的语料路径。

`ingest` 如果发现交接文件旁有 `.json.sha256`，会先校验原始字节。不匹配或文件不可解析时直接退出，尚未识别可信批次，不记录为已接收。合法 JSON 的批次验证失败会在账本中保存失败尝试，返回非零退出码；修正文件后重复 ingest 即为重试，不另设一套重试状态机。

可以在子命令前加 `--registry <独立账本路径>` 隔离练习；export 还可指定 `--output`、`--feedback`。不要把 output 指向 A 原始交接文件或账本文件。当前源快照版本在导出回执中另列 input_snapshot_revision，不向 C 的严格顶层格式擅加字段。

当前生成的 workspace 是当时输入集合的一致副本，CLI 导出前再次检查输入版本是否变化；变化则要求重试，不自动发布。未部署长期监听任务。不同批次的来源信息和原文在账本中保存，C 的 effective 文件沿用原契约，只提供有效知识结果。
